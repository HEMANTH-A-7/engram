### Hard-won Cognee+Ollama config facts (don't relearn these)
- **Endpoints differ by role**: LLM `LLM_ENDPOINT=http://localhost:11434/v1` (instructor uses a raw OpenAI client); embeddings `EMBEDDING_ENDPOINT=http://localhost:11434/api/embed` (native path). `core/config._openai_base()` normalizes either back to `<host>/v1` for our own calls.
- **Bare model names** (no `ollama/` prefix): the native adapters pass the name verbatim and Ollama 404s on the prefix. `LLM_MODEL=gemma4:latest`, `EMBEDDING_MODEL=nomic-embed-text`.
- **Extraction model = gemma4**, NOT llama3.2:3b. 3B models echo the JSON *schema* instead of an instance → validation fail. **→ D5 below.**
- **`LLM_TEMPERATURE=0.3`**: at temp 0, instructor retries are identical, so a single null-for-required-string response never recovers. A small temp makes retries vary and succeed. Tradeoff: extraction is nondeterministic (acceptable; eval set is fixed, average over runs).
- Needs `transformers` (BERT tokenizer `HUGGINGFACE_TOKENIZER=bert-base-uncased`, one-time download) and `COGNEE_SKIP_CONNECTION_TEST=true` (30s pre-flight < Ollama cold start).
- Cognee is graph-provider **ladybug** + vector by default; storage pinned to repo `.cognee_data/` + `.cognee_system/`.
- **Ollama structured-output retries are hardcoded to 2** (`cognee/.../llm/ollama/adapter.py`, not env-configurable), and `cognify()` batches every fact into one pipeline run — one flaky extraction (gemma4 emitting a null `description`) aborts the whole batch. Observed 3/3 attempts needed on an 8-fact benchmark run, so this isn't rare. `benchmark/harness.py` retries the whole ingest+cognify batch (bounded at 3, logged via `cognify_attempts`) to compensate; `core/store.py` (the baseline pipeline) is left vanilla.
- **Raw CHUNKS retrieval latency is high locally**: p50 ≈13s / p95 ≈21s per query on the 8-fact benchmark set, on local Ollama CPU (no GPU). Expected given the hardware — real baseline number, not a bug to chase.
- **gemma4 echoes the JSON-schema wrapper, not randomly but systematically**: instructor's `json_mode` embeds the target schema as text in the system prompt (it literally contains a `"properties"` key). For our narrow `Triple(subject, relation, object)` schema, gemma4 kept nesting the actual values under a `properties` key (`{"properties": {"subject": "Alice", ...}}`) instead of returning them top-level — and did this on the *first* generation of every one of 3 outer retry attempts (6/6 LLM calls in one observed run), so blind retrying alone never recovered it. Fix: a Pydantic `model_validator(mode="before")` on `Triple` (`core/ingest.py`) that unwraps this exact shape when the nested values are plain strings (the "self-correction" response instructor triggers on its own internal retry usually has real values, just misplaced) — repairs the response instead of burning a retry on a fixable shape. Still correctly rejects the case where `properties.*` are themselves schema-shaped dicts (no real value present).
- **Conflict-case eval sentences must not restate the stale value in the current fact's own text.** Original `CONFLICT_CASES`/`test_ingest.py` used transition sentences like *"Alice moved from Boston to Seattle, so she now lives in Seattle."* as the *update* — but that sentence's raw text (which is legitimately the only thing indexed for the current fact) contains "Boston" as a substring, so any stale-value leak check on retrieved text false-positives even under perfect resolver behavior. Reworded all 3 `CONFLICT_CASES` + the integration test's update sentence to be self-contained (e.g. "Alice now lives in Seattle.") — this is a broader property to keep in mind when adding future eval cases: an update fact's own current-state description must never happen to contain the value it's replacing.
- **`EVICT_THRESHOLD` must exceed the score floor of a default-importance fact, or nothing is ever evictable.** As recency → 0 and frequency → 0 (fully decayed, never accessed), `score → WEIGHT_IMPORTANCE * 0.5 = 0.10` for a fact left at the neutral default importance. The originally-planned `EVICT_THRESHOLD = 0.10` made eviction mathematically unreachable (`score < threshold` is never true when the floor equals the threshold) — caught by hand before running any tests, fixed to `0.15` (still a strict subset of `WARM_THRESHOLD = 0.25`). Any future retuning of the weights/thresholds needs to re-check this floor-vs-threshold relationship.
- **A single access can contribute the *entire* frequency weight, not a fraction of it.** `frequency = log1p(access_count) / log1p(max_access_count)` is normalized per-dataset — if a fact is the *only* one with any accesses (or ties the max), one access gives `frequency = 1.0`, the full `WEIGHT_FREQUENCY = 0.3`. Combined with the `0.1` importance floor, that's `≥0.4`, comfortably in "warm" even after 60 simulated days with zero further access. First caught this via a wrong test assertion (`test_accessed_fact_resists_eviction_longer` originally expected eviction to still happen) — the formula was right, the test's expectation was wrong; fixed the assertion to check "not evicted, tier=warm" instead.
- **`evict()`'s regret-detection trick**: reusing `valid_to` (the same column `write()`'s supersede path stamps) means `current_facts()`'s existing `valid_to IS NULL` filter excludes evicted facts for free — no new query logic needed. `evicted_at` (left NULL by an ordinary supersede) is what distinguishes "evicted" from "superseded", letting `write()` detect a revival (a write to a canonical key whose most recent row was evicted, not superseded) as a pure property of the resolver's own history — no dependency on Cognee/search-ranking to measure regret.
- **A pre-Bucket-4 `.resolver_data/facts.db` needs an explicit migration.** `CREATE TABLE IF NOT EXISTS` in `_SCHEMA` only applies to brand-new databases; an existing file keeps its old 11-column shape forever. Discovered when the integration test hit `sqlite3.OperationalError: no such column: evicted_at` against the real (already-populated-from-Bucket-3) `.resolver_data/facts.db`, since unit tests all use fresh `tmp_path` DBs and never exercised this path. Fixed with an idempotent `_migrate()` (checks `PRAGMA table_info`, `ALTER TABLE ADD COLUMN` for whatever's missing) called from `configure()`.
- **An empty Cognee index raises `NoDataError` on search, it doesn't return an empty hit list.** `resync_active()` rebuilding from zero hot facts (everything evicted) means `store.reset_and_load(dataset, [])` — Cognee then raises `cognee.modules.retrieval.exceptions.exceptions.NoDataError` on the next search rather than returning `[]`. The integration test treats catching this exception as equivalent to "not searchable" (`_search_text()` helper) rather than expecting a graceful empty result — worth remembering for any future code that searches a dataset that might have zero indexed facts.
- **D5 resolved: neither model is reliably "the good one" — cost-aware routing has to be a cascade, not a static split.** Manually testing `llama3.2:3b` vs `gemma4:latest` against `core/ingest.py`'s real retry policy on 10 sample facts found `llama3.2:3b` succeeded 5/10 (avg 4.3s/call) while `gemma4:latest` succeeded 7/10 but averaged 38.4s/call (~9x slower) — gemma4 is *more reliable and much slower*, not simply "the strong model." This rules out a static "routine → small, ambiguous → large" split; `core/router.py`'s `route_extract_triple` instead tries the small model for 2 attempts, escalates to the large model for up to `MAX_EXTRACT_ATTEMPTS` more attempts only on failure. Confirmed again during Bucket 5 integration testing: even the *full* 5-attempt cascade can exhaust and raise `RuntimeError` on a trivial fact ("Alice lives in Boston.") — local structured-output extraction is genuinely unreliable enough that total failure is a real, non-hypothetical outcome callers of `ingest.remember()` must expect, not just a theoretical edge case.
- **"$ cost" in this bucket is reference cloud pricing, not real spend, and that's stated in the data itself.** This project runs 100% locally against Ollama — actual spend is $0. `core/router.py`'s `cost_report()` prices real prompt/completion token counts (from each response's own `usage` field) against published 2026 rates for comparably-sized hosted models ($0.10/M for the ~3B tier, $0.20/M for the ~8-9B tier — Together AI / pricepertoken.com), and every report carries a `pricing_note` string saying exactly this rather than letting a bare dollar figure imply a real bill.
- **The ambiguity heuristic that gates LLM-based conflict judgment is deliberately a cheap string proxy, not semantic similarity.** `core/resolver.py`'s `_is_ambiguous()` flags a conflict only when one object string is a case-insensitive substring of the other (e.g. "Boston" → "Boston, MA") — catching refinements/typos while leaving the common case (fully non-overlapping values like "Boston" → "Seattle") on the fully deterministic, zero-LLM-call path. This is intentionally a proxy, not a real similarity measure — it won't catch a semantically-ambiguous conflict phrased with no string overlap, and that's an accepted false-negative in exchange for keeping "routine" conflicts free, matching the spec's own routine-vs-ambiguous split.
- **Cognee's own internal `cognify()` extraction model is explicitly out of scope for this router.** Cognee exposes a per-context LLM override (`set_database_global_context_variables(dataset, user_id, llm_config=...)`, a ContextVar in `cognee/context_global_variables.py`), but it requires a `user_id` this single-tenant project has no plumbing for, and Cognee's own multi-node `KnowledgeGraph` extraction is a *harder* extraction problem than this project's narrow single-triple schema (more failure surface, not less) — not a good first target for a 3B cascade. The router controls only this project's own three call sites (extraction, conflict judgment, summarization).
- **Real-Ollama extraction can return a schema-valid but semantically empty field.** On a dense, multi-clause sentence, `gemma4:latest` returned `Triple(subject='Alice', relation='', object='senior software engineer at a large tech company in Boston')` — a `Triple` that validates cleanly (empty string is a legal `str`) but has clearly mis-parsed the sentence into the wrong fields. `route_extract_triple`'s contract is "schema-valid or raises," not "semantically correct" — callers needing semantic guarantees would need an additional check this bucket doesn't add.
- **FastMCP's `@mcp.tool()` returns the original callable, so tool bodies stay directly testable.** `mcp_server/server.py`'s four tools are plain `async def` functions decorated with `@mcp.tool()` (mcp 1.28.1); the decorator registers the tool *and* returns the function unchanged, so `tests/test_mcp_server.py` imports and `await`s them directly (no client round-trip needed for the fast suite). Verified this against the real API before building rather than assuming it. The separate `tests/test_mcp_server_integration.py` still does one real `mcp.client.stdio` subprocess handshake (`list_tools`) to prove the actual server *binary* advertises all four tools, not just that the functions work when imported.
- **`memory_write`/`memory_forget` are serialized under an `asyncio.Lock` because they wipe the whole Cognee data root.** Both call `store.reset_and_load` (full reset + cognify), which prunes Cognee's *entire* configured data root, not one dataset — two overlapping calls would race destructively. `mcp_server/server.py`'s module-level `_pipeline_lock` makes them mutually exclusive. Reads (`memory_search`, `memory_stats`) deliberately don't take the lock. This is the MCP-layer expression of the same single-active-dataset constraint that's held since Bucket 1.
- **`memory_search` must treat an empty index as empty results, not an error.** After `memory_forget` evicts the last fact, `resync_active` rebuilds the index from zero survivors, and Cognee then raises `NoDataError` on the next search (it doesn't return `[]`). Surfaced during integration-test design of the write→search→forget→search flow: an agent-facing tool crashing on "everything's been forgotten" is wrong, so `memory_search` catches `NoDataError` and returns `{"hits": [], "hit_facts": []}` — mirroring the `_search_text` helper the Bucket 4 consolidation integration test already uses.
- **`importance` in `memory_write` metadata is accepted-but-ignored, on purpose.** `ingest.remember` doesn't thread an `importance` value through to `resolver.write` yet (Bucket 4 left importance as a neutral-0.5 slot with no real signal wired in), so `memory_write` documents `metadata["importance"]` as accepted-but-currently-ignored rather than silently dropping it or pretending to honor it. Same honesty pattern as the rest of the project — a visible stub beats an invisible no-op.
- **Registration is proven on the two installed clients; Codex is doc-only because it isn't installed — and that's fine, the binary is identical.** Committed `.mcp.json` (Claude Code, project-scoped) + written `~/.gemini/config/mcp_config.json` (Antigravity, was empty) both point at the same `uv run --directory <repo> python -m mcp_server.server` command. Codex CLI isn't installed on this machine, so `mcp_server/REGISTRATION.md` carries a paste-ready `[mcp_servers.memory_layer]` TOML block for `~/.codex/config.toml` instead — the spec's "same binary, no code changes between them" means adding Codex later is a one-line config paste, not a code change. (TOML table keys can't contain `-`, so Codex's server name is `memory_layer`; the tool names are identical everywhere.)
- **Building the dashboard exposed that two of its five spec cards had no backing metric — the visualization surfaced a real measurement gap, not just a rendering task.** Conflict accuracy, cost/1k, and regret rate were already computed by earlier buckets, but "tokens saved vs raw history" and "storage growth over time" had nothing behind them. Bucket 7 added `run_tokens_eval` + `run_storage_growth_eval` to `benchmark/harness.py` to make all five cards real, rather than shipping placeholder charts. A dashboard is a forcing function that reveals which claimed metrics actually exist.
- **Token counts are a documented `≈ chars/4` estimate, on purpose, because `tiktoken` isn't offline-safe.** `tiktoken`'s BPE vocab downloads from the network on first use, which would break the project's hard offline guarantee. `benchmark/harness.py::_estimate_tokens` uses `round(len(text)/4)` and says so in its docstring and in `tokens.json`'s `note` field. The card's headline is the raw-vs-extended *ratio* (30.1% saved on the pre-labeled set), which a consistent estimator captures faithfully regardless of exact tokenizer — same honesty pattern as the cost router's "reference pricing, not real spend."
- **Chart.js is vendored locally (`dashboard/static/vendor/chart.umd.min.js`), never a CDN.** A CDN `<script>` tag would make the dashboard silently depend on network access at view time, violating the offline rule the same way a cloud API would. The library is fetched once at build time (`curl` from jsDelivr) and committed, so `uv run python -m dashboard.app` renders with zero network requests.
- **The two new storage/token evals are deliberately LLM-free.** They reuse a pre-labeled `_VERSIONED_FACTS` set (hand-written conflict-update triples + `FORGET_CASES`) written via `resolver.write` directly, exactly like `run_forgetting_eval` — no extraction. These metrics measure *storage footprint and versioning compaction*, not extraction quality, so paying the slow/flaky LLM path for them would be waste; it also keeps them in the fast test suite. Honest scope note in each eval's `note`: the storage series isolates Bucket 3 versioning compaction (`without` = every write, `with_` = current non-superseded facts); consolidation/eviction is reported separately as regret rate, because backdating per-fact ingestion time (needed to evict mid-series) isn't in the resolver's public API.
- **An MCP stdio server's stdout is the JSON-RPC wire — nothing else may write to it, and only a real client catches a violation.** Testing the server with an actual `mcp.client.stdio` client (write→search→stats→forget) exposed that Cognee's DB layer prints chatter to stdout during `cognify()` ("table already exists, skipping creation"), which a real client rejects as `JSONRPCMessage` validation errors mid-`memory_write`. The in-process and `list_tools`-only tests never caught it — direct calls send stdout nowhere harmful, and `list_tools` triggers no `cognify()`. Fix in `mcp_server/server.py::main()`: hand the MCP writer a *private* `os.dup(1)` of the real stdout, then redirect the process's own stdout to stderr at both the fd level (`os.dup2(2, 1)` — catches raw/handler writes to fd 1 regardless of cached stream references) and the Python level (`sys.stdout = sys.stderr` — catches `print`), driving the low-level `stdio_server(stdin=…, stdout=<private wire>)` instead of `mcp.run()`. Lesson: "tests pass" ≠ "works over the real transport" for a stdio protocol server; a genuine client round-trip that exercises the noisy path is the only proof. **Regression test landed** (`tests/test_mcp_server_integration.py::test_memory_write_round_trip_keeps_the_wire_clean`): a real `mcp.client.stdio` client drives `memory_write` (the cognify path) and asserts the protocol survives and the payload shape is valid. Honesty caveat found while wiring it up (2026-07-03): the specific corruption no longer reproduces in the current stack — reverting `main()` to `mcp.run()` and re-running the test warm, cold, single-write, and full write→search→stats→forget all stayed green, because Cognee 1.2.2 now emits its DB chatter to *stderr*, not stdout, on these paths. So the test is a guard **by construction** (a real client validates every wire line, breaking on any stdout leak) rather than a demonstrated red→green; the fix stays as correct defense-in-depth.
- **`memory_forget(id)` was undiscoverable, so `memory_search` now returns ids.** A client (Claude alone) had no way to learn a fact's id — `memory_search` returned only hit texts and `memory_stats` only counts — so the id-based `memory_forget` was unreachable from a real session. Fix: `memory_search` now returns `hit_facts`, an index-aligned list of `{id, subject, relation, object, text}` alongside the unchanged `hits: [str]` (additive, non-breaking — the dashboard and the ` " ".join(hits) ` test assertions keep working). Cognee doesn't thread resolver ids through its own pipeline, so the id is recovered by exact-text match against `resolver.current_facts` — the same 1:1 `Fact.text` invariant `record_access_from_hits` already relies on; an unmappable hit (anomaly) gets `id: null` rather than a guess. Verified end-to-end: the integration test now discovers the id from `hit_facts` and forgets it, no resolver side channel.

- **`run_conflict_eval()` legitimately takes ~20–40 min wall-time on CPU Ollama — any external timeout must budget for it.** The eval is ~6 `cognify()` batch runs (3 cases × resolver+naive datasets) at ~3–5 min each, *plus* instructor/harness retries. A 420s/attempt watchdog looked like "gemma4 is permanently stuck" but was actually killing healthy runs; with a 3600s budget the same eval passed on attempt 1. Slowness and flakiness are different failure modes here — diagnose wall-time before blaming the model.
